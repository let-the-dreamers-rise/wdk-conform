# Findings

Run against the versions pinned in `package.json` (October 2026). Reproduce everything below
with `npm ci && npm run conform`. Full evidence for each case is in `report/report.json`.

| # | Module | Finding | Impact |
|---|---|---|---|
| 1 | wdk-wallet-btc | Default config derives under the testnet coin type but shows mainnet addresses | **High**: the seed does not restore in other Bitcoin wallets |
| 2 | wdk-wallet-btc | Unknown network names (`"mainnet"`, `"livenet"`) are accepted silently and hit the same path | **High**: a one-word typo triggers finding 1 |
| 3 | wdk-wallet-btc | Unhardened index ≥ 2^31 is accepted and derives the hardened key | Medium: two path strings for one key; `path` and `index` misreport it |
| 4 | wdk-wallet-ton | Unhardened segments are silently derived as hardened | Medium: `path` reports a key the account does not hold |
| 5 | evm, btc, solana, ton, tron | Leading zeros (`01`, `00'`) are accepted, so one key has many path strings | Low: already fixed in wdk-wallet-aptos, not in the others |
| 6 | evm, btc, tron | `account.index` is `NaN` (btc, tron) or `undefined` (evm) when the last segment is hardened | Low |

What passes, and matters as much: the EVM module's own BIP-32 implementation
(`src/memory-safe/hd-node-wallet.js`) matches the reference on all 17 official BIP-32 vector
chains and 500 random seed/path cases. Every module's `sign()` output verifies with an
independent verifier for that chain's scheme (EIP-191, BIP-137, TRON V2, ed25519 for
Solana/Aptos, and WDK's TON safe-sign hash). All default `getAccount(i)` addresses match
MetaMask, Phantom, TronLink and Petra conventions.

## 1. wdk-wallet-btc: mainnet addresses derived under the testnet coin type

Leave `network` out of the config, which the docs allow ("Default: `"bitcoin"`",
`docs/sdk/wallet-modules/wallet-btc/configuration.mdx`). The module then:

- picks the coin type with `config.network === 'bitcoin' ? 0 : 1` (so `1'` when unset),
  in `src/wallet-account-btc.js:123` (npm 1.0.0-beta.17) and `getBtcDerivationPathPrefix` in
  `src/signers/seed-signer-btc.js` (main);
- encodes the address with `networks[config.network] || networks.bitcoin` (mainnet when unset).

So the official BIP-84 test seed (`abandon ... about`) gives:

| | path | first address |
|---|---|---|
| BIP-84 vector, Sparrow, Electrum, BlueWallet, Ledger | `m/84'/0'/0'/0/0` | `bc1qcr8te4kr609gcawutmrza0j4xv80jy8z306fyu` |
| WDK, default config | `m/84'/1'/0'/0/0` | `bc1q6rz28mcfaxtmd6v789l9rrlrusdprr9p276ldv` |

Funds sent to a default WDK wallet appear missing when the user restores the seed anywhere
else. The same happens with `bip: 44`. The upstream unit tests pin this behaviour: the fixture
`COIN_NODE_PATH = "m/84'/1'"` is labelled "the default configuration" next to an
`expect(signer.network).toBe('bitcoin')` assertion. Fixtures generated by the code under
test cannot catch this; an independent reference does.

Fix: [`patches/0001-fix-default-to-the-mainnet-coin-type-when-no-network.patch`](patches/0001-fix-default-to-the-mainnet-coin-type-when-no-network.patch) (three-line
change plus fixture updates and two regression tests, one of them the BIP-84 vector). The
module's unit suite shows no new failures with it.

Migration note for maintainers: apps that already shipped with the default config hold user
funds under `m/84'/1'`. After the fix they should also scan that path once (or sweep it), so
upgrading does not make balances disappear.

## 2. wdk-wallet-btc: unknown network names accepted

`{ network: 'mainnet' }`, `'Bitcoin'`, `'livenet'` and `'main'` all construct a wallet with
mainnet addresses at `m/84'/1'/...`, which is finding 1 again. The fix above throws
`ValueError` for any name other than `bitcoin`, `testnet` and `regtest`.

## 3. wdk-wallet-btc: `0'/0/2147483648` derives `0'/0/0'`

`bip32` treats any index ≥ 2^31 as hardened. WDK passes the path straight through, so
`getAccountByPath("0'/0/2147483648")` returns the key at `m/84'/0'/0'/0/0'` while reporting
`path = m/84'/0'/0'/0/2147483648` and `index = 2147483648`. EVM and Tron reject the same input.

## 4. wdk-wallet-ton: unhardened segments silently hardened

`micro-key-producer` is called with `forceHardened = true`, so `getAccountByPath("0")` returns
the key for `m/44'/607'/0'` but reports `m/44'/607'/0`. SLIP-0010 ed25519 has no unhardened
derivation, so the input should be rejected. Solana and Aptos already reject it.

## 5. Leading zeros alias paths

`"0'/0/01"` and `"0'/0/1"` derive the same key on evm, btc and tron; `"00'"` and `"0'"` on
solana and ton. wdk-wallet-aptos rejects these on purpose (its source says it is "so distinct
path strings cannot alias the same derived key"). The other modules should share that check.

## 6. `index` getter

`+path.split('/').pop()` gives `NaN` for a hardened last segment (`0'/0/0'`) on btc and tron; evm returns `undefined`. Expected: the numeric index without the hardened marker, as solana, ton and aptos do.

## Not bugs, but worth documenting (interoperability notes)

- **Spark** derives under `m/44'/998'/...` (WDK's `Bip44SparkSigner`). The official Spark SDK
  default key generator uses `m/8797555'/...`. A WDK Spark seed will not show the same
  identity in wallets built on the default Spark SDK. Not yet covered by an automated check:
  the Spark module needs a live network to build an account.
- **TON** `sign()` uses ed25519 over `sha256(0xffff || "ton-safe-sign-magic" || message)`. TON
  Connect `signData` verifiers use a different envelope, so dApps cannot verify these.
- **Aptos** `sign()` signs raw message bytes. AIP-62 wallets sign the `APTOS\nmessage: ...`
  envelope, so dApps that verify `signMessage` output will reject them.
- **Bitcoin** `sign()` emits BIP-137 segwit headers (39-42). Bitcoin Core's `verifymessage`
  only handles legacy addresses; BIP-322 is the standard for bc1 addresses.
